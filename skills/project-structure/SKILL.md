# Project structure

The decisions every role makes about structure: where a thing goes, how big it gets before it
splits, and what it is called. Deliberately short — it is preloaded into four agents, so every
line costs context on every run.

For the *mechanics* of a split, and for config code, invoke `python-implementation`. For the
skeleton files a new repo or package starts from, invoke `workspace-scaffold`. For what goes
*inside* a file, see `python-style-guide`.

## 0. New projects vs. existing repositories

§1 is the layout a **new** project gets. On a repository that already has a package root, **the
existing layout wins** — match what is there.

The reason is concrete, not stylistic: adding `src/<pkg>/` beside an existing top-level
`mypkg/` gives the project two import roots, a package the existing `pyproject.toml` does not
install, and tests that import whichever copy is first on the path. That failure is silent and
expensive to unpick — a worse outcome than an unfashionable layout.

So on an existing repo: put new modules where its convention puts them, name them the way it
names things, register entry points the way it registers them. Everything else here still
applies — the size limits, config placement, and naming are about keeping files
comprehensible, and they hold in any layout.

Migrating a flat repo to `src/`, or a single package to a workspace, is a real change with real
value, but it is a change: it belongs in a `/project-workers:plan-change` run of its own, never smuggled into a
section build. If a repo's layout is causing actual problems, file a follow-up saying so.

## 1. Layout

Multi-package repository — a `uv` workspace, one directory per package under `packages/`:

```
<repo>/
├── pyproject.toml              workspace root: members, ruff, pylint, import-linter config
├── mkdocs.yml                  docs site; API pages under docs/api/
├── README.md                   generated by /project-workers:finalize-project
├── CLAUDE.md
├── docs/                       planning docs: architecture.md, decisions.md, packages/<pkg>/…
└── packages/
    └── <pkg>/
        ├── pyproject.toml      this package; [project.scripts] → <pkg>.cli:<command>
        ├── README.md           generated by /project-workers:finalize-project
        ├── tests/
        │   ├── conftest.py
        │   ├── fixtures/
        │   ├── unit/           mirrors src/<pkg>/ path for path
        │   └── integration/
        └── src/<pkg>/
            ├── __init__.py     THE PUBLIC SURFACE: re-exports + __all__ (see below)
            ├── configs.py      all settings for this package
            ├── cli.py          CLI commands; one function per command (finalize-package)
            ├── pipelines/      cross-section flows; written by /project-workers:finalize-package
            └── <section>/
                ├── __init__.py EMPTY
                ├── README.md   the section README
                └── <module>.py
```

Single-package repository: the same shape without `packages/` — `pyproject.toml`, `tests/`,
and `src/<pkg>/` at the root. Shared code in a workspace is its own package, never a
top-level `common/` outside `packages/`.

Rules:

- `src/` layout. Nothing importable lives at the repository root.
- **The top-level `__init__.py` of a package is its public surface.** It exposes only the
  names consumers outside the package need, listed in `__all__`, resolved lazily so importing
  the package costs nothing until a name is used. It is written by `/project-workers:finalize-package` from the
  package's `surface.md`, and by nothing else. **Every nested `__init__.py` is empty.**
  *Project convention, not Google's* — the pattern and the reasoning are in `python-style-guide`.
- **Imports inside a package** come from the defining module: `from data.ingest.loaders import
  load_bars`, never `from data import load_bars` from within `data`. **Imports across packages**
  come from the provider's top level only: `from data import load_bars`, never
  `from data.ingest.loaders import load_bars` from inside `analysis`. import-linter enforces
  both directions (`workspace-scaffold` §3); a violation is a build failure, not a style note.
- Dependencies between packages point one way, in the order `docs/architecture.md` declares.
  A package never imports a package above it.
- **There is no `scripts/` directory.** Anything runnable is a command function in
  `src/<pkg>/cli.py` (or `cli/` when there are many), registered under `[project.scripts]` as
  `<pkg>-<verb> = "<pkg>.cli:<function>"`. An entry point must be importable from the installed
  package, and a file outside `src/<pkg>/` is not — a `scripts/` directory beside `src/` looks
  tidy and cannot be registered. A command function does argument handling and one call into a
  pipeline; no logic.
- Tests mirror source paths: `src/data/ingest/parsers.py` → `tests/unit/ingest/test_parsers.py`.
- Lint, import-linter, and docs configuration live at the workspace root, once. A package's
  `pyproject.toml` carries only what is specific to it.

## 2. Size limits

| Unit | Soft | Hard | Enforced by |
|---|---|---|---|
| Module (lines) | 400 | 1000 | pylint `C0302` |
| Function/method (statements) | 30 | 50 | ruff `PLR0915` |
| Cyclomatic complexity | 8 | 10 | ruff `C901` |
| Positional parameters | 4 | 5 | ruff `PLR0913` |
| Class (lines) | 200 | 400 | review |
| Public methods per class | 12 | 20 | pylint `R0904` |
| Modules per package directory (excl. `__init__.py`, `configs.py`, `README.md`) | 8 | 12 | review |

**Soft means plan the split; hard means split before finishing the task.** The line and
statement limits match the linter defaults, so tooling rather than opinion decides. The 8/12
modules-per-directory figure is this toolbox's own, sized so a directory listing fits on one
screen. The soft statement limit is also the signal `python-style-guide` "Function shape"
uses: it says look for a seam, not cut here.

Who uses these, and how:

- **Architect** — a section whose responsibility clearly exceeds these limits is two sections.
- **Designer** — the **Module plan** lists files sized to the *soft* limits, never one module
  that will obviously blow past them.
- **Implementer** — the plan will sometimes be wrong. Check real sizes before finishing: past a
  hard limit, split now (invoke `python-implementation`); past a soft limit, note it in the
  return.
- **Reviewer** — anything past a soft limit without a note, or past a hard limit at all, is a
  finding.

## 3. Configuration placement

One `configs.py` per package holds every setting for that package as a `pydantic-settings`
class, with the env prefix `docs/architecture.md` assigns the package (`<PKG>_` by default).
No other module reads `os.environ` directly.

**Split rule:** when a section owns at least a third of the fields in `configs.py`, or
`configs.py` passes the soft module limit, move that section's fields into
`src/<pkg>/<section>/configs.py` as its own settings class, composed into the parent as a
nested field. The parent stays the single entry point; modules import the subsettings they
need from it rather than constructing their own.

The designer names which settings go in a section's `configs.py` as part of the Module plan.
`/project-workers:finalize-package` composes the section settings into the package's. For the code, invoke
`python-implementation`.

## 4. Module and package naming

- Packages and sections: a single lowercase token, `[a-z0-9-]+` — they become directory names
  and skill arguments (`/project-workers:implement-section data/ingest`). Modules: `snake_case` nouns —
  `indicators.py`, `bars/`.
- No `utils`, `helpers`, `misc`, or `common` at any level, except a shared package in a
  multi-package repo. A file literally named `utils.py` is a review finding once it passes 100
  lines, because nobody can tell you what belongs in it.
- One class per module when the class exceeds 100 lines; otherwise related small classes may
  share a module.
- Test files: `test_<module>.py`. Fixtures in `tests/fixtures/` or `conftest.py`, never inline
  data blobs over 20 lines.

Naming *inside* a file — functions, variables, constants, private members — belongs to
`python-style-guide`.

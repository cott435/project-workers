Write the package READMEs, the API pages, and the root `README.md`.

> **Guard.** If you can see earlier conversation turns, or you have an `AskUserQuestion` tool, you are
> running in the main conversation rather than as the `documenter` subagent — the agent is not
> registered, usually because the project-workers plugin was installed or updated after Claude
> Code started. Stop, tell the user to run `/reload-plugins` (or restart Claude Code),
> verify with `/agents`, and re-run.

## Preconditions

Run these and record the results. Every one is guarded, because this skill has to work on a
half-finished repo — one package shipped, two planned — reporting a gap is useful, failing on
a missing file is not.

```
ls docs/architecture.md docs/decisions.md 2>/dev/null
ls docs/packages/*/contract.md docs/packages/*/interface.md 2>/dev/null
grep -c '^- \[ \]' docs/followups.md 2>/dev/null || echo 0
grep -rn 'TODO(decision' --include='*.py' packages/ src/ 2>/dev/null | grep -vE '\.venv|site-packages' | wc -l
ls docs/plans/*/integration.md docs/plans/synced.md 2>/dev/null
```

If `docs/architecture.md` is missing entirely, fall back to inferring packages from
`packages/*/` or `src/*/`, and say so in **Known gaps** — `/project-workers:plan-repo` or `/project-workers:map-project` is
the fix.

## Procedure

1. **Find the documents** per your instructions: packages from the repo contract, sections from
   each package contract, never by sweeping the tree. Read each package's `interface.md` (if
   any), its section READMEs, `docs/architecture.md`, `docs/decisions.md`, `docs/followups.md`,
   and `docs/plans/synced.md`.

2. **Preserve hand-written READMEs.** For every README you are about to write — root or
   package — if the file exists and does not carry the marker line this skill writes, it was
   written by a person and may hold things no generated document knows. Copy it to
   `docs/readme-previous.md` (root) or `docs/packages/<pkg>/readme-previous.md` before replacing
   it, and say so in your return.

3. **Write each package README** — `packages/<pkg>/README.md` (or the root's `README.md`
   section for a single-package repo). Start with `<!-- generated by /project-workers:finalize-project -->`,
   then:

   - **What it is** — from the package contract's Purpose, and which repo shapes it provides.
   - **Public surface** — the **Public names** table from `interface.md`, one line each with the
     signature. If there is no `interface.md`: "not finalized — run `/project-workers:finalize-package <pkg>`",
     and list the sections' `Public: yes` rows as *intended*.
   - **Pipelines and CLI commands** — from `interface.md`; exact commands with their arguments.
   - **Sections** — the Sections table, each row linking to that section's README.
   - **Configuration** — env prefix and every env var from `interface.md` and the section
     READMEs, deduplicated; conflicting defaults listed both ways and flagged.
   - **Running and testing** — the Toolchain's one-package commands.
   - **Consumers** — the snapshot from `interface.md`, labeled with its date.
   - **Key decisions** — `decided` entries scoped to this package, one line each.
   - **Known gaps** — this package's share of the list in your instructions.

4. **Keep the docs site whole.** `/project-workers:finalize-package` writes `docs/api/<pkg>.md` and its nav
   entry as each package ships; here you regenerate `docs/index.md` from the root README you
   are about to write (same content, site-relative links), confirm every shipped package has
   its API page and nav entry — writing any that is missing, in the same shape (`::: <module>`
   per providing module in **Public names**, plus `::: <pkg>.cli` and the pipeline modules) —
   and run `mkdocs build --strict`. A failure is a **Known gaps** entry naming the module.

5. **Write the root `README.md`.** Start with the marker line, then:

   - **What it is** — two paragraphs from the repo contract's Goal and Non-goals.
   - **Packages** — the Packages table in dependency order, each row linking to that package's
     README, with its status derived: *planned* (contract only), *built* (all section READMEs),
     *shipped* (`interface.md`).
   - **How the packages connect** — one paragraph per boundary from the repo contract, naming
     the shapes that cross it and the public names that carry them.
   - **Quick start** — install, configure, run, test, build docs. Exact commands from the
     Toolchain; every env var from every package, deduplicated by prefix.
   - **Entry points** — CLI commands and pipelines collected from the `interface.md` files.
   - **Key decisions** — every `decided` entry scoped `repo`, one line each; package-scoped
     ones are in the package READMEs.
   - **Documentation map** — links to `docs/architecture.md`, `docs/decisions.md`,
     `docs/followups.md`, `docs/reviews/`, `docs/plans/`, each `docs/packages/<pkg>/`, and each
     package README.
   - **Known gaps** — the full list per your instructions.

6. Modify no file but the READMEs above, `docs/index.md`, `docs/api/*.md`, the `nav` list in
   `mkdocs.yml`, and the `readme-previous.md` copies from step 2.

## Return

Paths of every README and API page written, whether any previous README was preserved, the
docs build result if run, and the Known gaps list — unfinalized packages, missing section
READMEs, unchecked follow-ups, open decision markers, decided-but-unapplied decisions, unsynced
plans, provisional consumes — so the user sees what is outstanding without opening a file.
